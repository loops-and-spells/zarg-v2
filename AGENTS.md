# Agent Guide

Rules for any agent (Claude, Codex, etc.) working in this repo.

## Toolchain

- **mise** manages every tool version. `mise.toml` is the source of truth.
- **bun** is the JavaScript runtime, package manager, test runner, and script runner.

## Layout

Monorepo. Every module lives in its own package under `packages/<name>/`.

```
mise.toml        # tool versions + monorepo root (config_roots = packages/*)
package.json     # bun workspaces = packages/*
packages/<name>/
  mise.toml      # this package's tasks (build, test, dev, ...)
  package.json   # name: @zarg/<name>
```

- One package = one module. No cross-package imports through relative paths; depend on the package by name (`"@zarg/<name>": "workspace:*"`).
- Tool versions live only in the root `mise.toml`. Package `mise.toml` files define tasks only.
- One `bun.lock` at the root. Run `bun install` from the root.

## Packages

- `packages/graph` (`@zarg/graph`): JSON graph store under `.zarg/graph`: snapshot, queries, diff.
- `packages/highlight` (`@zarg/highlight`): syntax highlighting as data, no dependencies: `highlight(lang, source)` → lines of spans with token kinds (keyword, id, comment, title, flow, string, number); platforms map kinds to their theme. Knows zarg's Gherkin; `@zarg/markdown` draws those fences with the host's colours.
- `packages/tokens` (`@zarg/tokens`): the design language: token keys (surfaces, text, intent, identity, severity, status, syntax), a platform-free `Theme` (keys to colour names, aliases resolved once) over a per-platform `Palette` (terminal truecolor, 256, 16; web dark, light), both Effect services (`Palette.on(platform)`, `Palette.terminal` from `ZARG_THEME_COLORS` / `COLORTERM` / `TERM`; `Theme.layer`). Plugins name intent, identity and severity keys only.
- `packages/frontmatter` (`@zarg/frontmatter`): the parsable data at the top of a Markdown file (a YAML subset, no dependencies, so it runs in the plugin sandbox): `parse(md) → { data, body }`, `stringify`. Plans keep `scenario`, `hash`, `title` there.
- `packages/audit` (`@zarg/audit`): `zarg audit`, the one CI check (`mise run audit`, part of `verify`): graph structure (invalid node files, broken edges), lints over the whole graph, completeness (gherkin's agenda), intent coverage, code (scenarios against their `@scenario` tags: untagged, planned-but-tagged, orphan; tags come from one `git grep` over tracked and untracked files, never `docs/` or `.zarg/evidence/`), proof (each built scenario proven, failing, stale or unproven by its e2e evidence at its current version, `@zarg/audit/version`) and evidence integrity; `--summary`, `--json`, `--junit <file>`, `--scenario <id>`; exit 0 complete, 1 a problem, 2 it could not run. Completeness, coverage and proof are warnings until the strict switch.
- `packages/e2e` (`@zarg/e2e`): end-to-end proof of the graph. Real `zarg` runs in a fresh project, user dir and home per journey (`world()`), through the CLI (`cli()`) and the TUI on a Bun PTY read through headless xterm (`zarg()`, recorded as an asciicast). `journeys/J-xxxx.test.ts` walk the graph's journeys: `journey("J-…")` and `proves("S-…", step)` (a scenario of that journey only; a model step retries once, then flaky) write `.zarg/evidence/<S-id>.json` with media (`buffer`, `cast`, `log` committed; binary media gitignored); only the latest run is kept. `mise run e2e` runs the fast tier (no model turns; the pre-push hook), `mise run e2e:full` every journey on the live zarg-router (`E2E_ZARG_ROUTER_URL`; the suite never starts, loads or warms a model). Its `test` task runs only the harness tests.
- `packages/catalog` (`@zarg/catalog`): the catalog, a static site for a human reader: an overview of the audit (every check, each journey's proven / failing / stale / unproven / planned), a page per intent (outcomes and the journeys serving them, constraints, questions), per journey (its scenarios in flow order, `@zarg/audit/flow`) and per scenario (its Gherkin, code linked to GitHub, its proof and evidence: buffers as frames, casts in the asciinema player, images, gifs, videos, logs), and search. `zarg catalog build [--out site]` writes it (deterministic; relative links, so any sub-path; only committed evidence media, nothing from a CDN; it empties only a directory that is its own); `mise run catalog` builds and serves it at http://localhost:4173.
- `packages/bm25` (`@zarg/bm25`): Okapi BM25 over short texts (`bm25(docs).score(query)`, `rank`), with a light stemmer; no dependencies.
- `packages/entities` (`@zarg/entities`): references to any plugin's data (`<plugin>/<kind>:<id>[@<version>]`), canonical versions, the entity shapes; no dependencies (runs in the sandbox). Plugins declare kinds (`entities` in `definePlugin`, with a tone and glyph) and serve them; graph node kinds are served for free; the host routes every ref to its one owner; plugins read them with the `Entities` power (scope `entities: { read, command }`), RLMs with the `Entities` service (typed per kind, `Entities:read` in the driver, plan and research presets); a table column with `ref: true` shows labels the core resolves.
- `packages/plugin` (`@zarg/plugin/server`, `@zarg/plugin/runtime`): the plugin runtime (each plugin in its own locked-down Bun process with `ses`, powers served by the host), grants (`~/.config/zarg/grants.json`), `PluginHost` and the write pipeline. Plugins load only through it; a test fails if another package imports a plugin.
- `packages/plugin-sdk` (`@zarg/plugin-sdk`, `@zarg/plugin-sdk/tools`): `definePlugin`, `defineView` and the power services plugins yield (`Secrets`, `Http`, `Files`, `Graph`, `Config`, `Agents`, `Views`, `Surfaces`, `Attention`, `Conversation`, `Inbox` (scope `inbox: true`: ask, which waits for the answer and pauses the call's deadline; post, whose answer comes to the plugin's `answered` method with its key; settle; update; list, its own open topics), `Entities.code(ref)` (a gherkin scenario's tagged code, redacted; scope `code: true`, "read the code tagged with scenarios": never secret, config or linked files), …); a plugin declares `surfaces` (where its views show; a `card` is how an agent looks in the grid) and marks tables `review: true` for the review queue; manifests, the checked build and `testPlugin`.
- `packages/plugin-gherkin` (`@zarg/plugin-gherkin`, contract `@zarg/plugin-gherkin/contract`): atomic Gherkin user action graph (states, scenarios, personas: who acts in each scenario, `by`, and journeys: named groups a scenario can be in, any number, `in`); its Journeys view is a nav item; intents (`I-`) with their outcomes (`O-`), constraints (`K-`) and questions (`Q-`): journeys serve outcomes, constraints bound journeys or scenarios; its Intents view is a nav item (`a` outcome, `k` constraint, `q` question, `e` edit, ⏎ answer, `d` remove).
- `packages/plugin-backlog` (`@zarg/plugin-backlog`, contract `@zarg/plugin-backlog/contract`): feedback (`backlog/feedback` entities, one committed file each under `.zarg/feedback/`), tied to the version of the entity it is about: stale once that changes. Each finished rehearse run reconciles the scenarios it walked: a finding of the same kind on the same scenario version merges into its open entry (however worded), and rehearse feedback it no longer reports closes, unless the operator flipped or noted it, or a triage round holds it (then it is only marked: not reported by run r-…). While a run walks a journey, that journey's feedback is locked (rows say rehearsing; flips, notes and Refine wait for the run's end). Its Feedback nav view is the triage hub: a journey's open feedback as on/off rows (the agent's first call, the operator flips with space; n adds the operator's note for refinement, ✎), the entries of a round queued or worked in triage read-only, with their status (queued, waiting, drafted, left out), the rest usable for the next round. The flow is Feedback → Triage → Backlog: Refine (r) queues the journey, a triage worker drafts its scenarios and its plan, and the plan lands in the Backlog lane; the Feedback view shows journeys and their feedback, not how far triage got (the round's rows say where they stand), and dropping a plan leaves its journey as if never planned. Plans (`backlog/item`, `.zarg/backlog/`) live on its Backlog nav view, a kanban (Backlog, Ready, Running, Review, Done; each lane scrolls and folds with z/Z; ⇧←→ moves a card; ⏎ or a click opens the drawer, an overlay panel over the board's right edge: the plan with its scenarios' versions, ✓ current or ⚠ changed; its tabs: Plan (to read: each changed scenario before and after, scenarios with the same change once, feedback in numbers) and For agents (every change, scenario version and feedback id); its buttons: Move ▾ (a lane), Drop, and Resync while a scenario changed: it takes the scenarios as they are now when its changes still fit, else sends the plan back to triage with its feedback moved onto them). A triage round's plans are linked: one waits (`after`) on those whose changes it needs, a scenario they also touch is not ⚠ changed for it, one after a dropped plan says so (⇠ after B-07 (dropped)) and is not taken, the drawer's Plan tab says what it waits on and what waits on it, and the journey stays planned until the round's last plan is dropped. The backlog raises inbox topics for what waits on the operator: a plan that needs them (Back to Ready, Drop), feedback rehearse routed to ask (one topic per journey, never one per entry: Keep them all on, Turn them all off, or go through them in Feedback with `o`), a scenario a round left out (Draft again, Leave it out), a drift (Reword the scenario, which keeps it on with that note; Change the code, which files a code plan: `kind: "code"`, no graph changes, never taken by the Planner, its topic's Done closes its feedback), and reports (a run's filing, a round's plans); a stale answer changes nothing and says so. A new plan waits in Backlog until the operator moves it to Ready; the core's Planner (`core/src/planner.ts`) applies a Ready plan's gherkin changes through the write pipeline, commits exactly those nodes and wakes reconcile; a landed pass moves it to Review.
- `packages/agent-triage` (`@zarg/agent-triage`, plugin name `triage`): triage, like rehearse: a `triage` rollup agent and N workers (`triage-1…N`, `[plugins.triage] workers`, default 2; the model answers without reasoning unless `reasoning = true`). Refine in Feedback queues a journey (as many as you like); each free worker takes the next in line through Refine (drafting scenario changes for the feedback that is on, following the operator's notes, with the `driver` model role; each proposal dry-run through gherkin's `dryRun` over the draft so far, the scenario shown with its states' ids and its code (what zarg does now); a proposal that reaches existing scenarios outside its round and journey (a reworded shared state) fails its try; a scenario whose tries fail is drafted again on its own, up to 3 rounds, before it is left out)) and Plan: the whole draft is dry-run and folded into small plans, as the RLM folds a task (the driver model groups the scenarios by concept, the decision model checks each group of several scenarios against ROMA's atomic criteria and a group that fails splits by dependency, at most 5 scenarios a plan, a plan waits on the plans whose changes it needs, and one that does not dry-run over them merges into them), and they go to the Backlog lane together (`plans`) (a round still at the old Re-rehearse step has its run stopped). The rollup shows the workers and the journeys in line (p pauses); a worker's view shows its journey's scenarios with each scenario's tries and change beside them (d drafts a scenario again). The core wakes it when the backlog's or rehearse's agenda changes. Drafts never touch the graph until the Planner applies a plan.
- `packages/agent-host` (`@zarg/agent-host`): the contracts between the core and agents: the `Thread` the core serves, the `AgentHost` a trusted agent gets, `defineTrustedAgent`. A library, not an agent.
- `packages/agent-zarg` (`@zarg/agent-zarg`): zarg, the conversational agent: the driver loop on `main`, the write gate, what next. A trusted first-party agent (`"zarg": { "runtime": "trusted" }` in its package.json): the core loads it by path from zarg's own packages and starts it; without it the core still serves and says why.
- `packages/agent-rehearse` (`@zarg/agent-rehearse`, plugin name `rehearse`): testers roleplay the Gherkin journeys on the decision model, only what is built (a story stops before a planned or untagged scenario; the run notes why) and with each scene's code in view (a scene: a scenario as a tester meets it in a story) (a `drift` finding: the scenario and the code differ, always the operator's call) (`/rehearse`; `journey` stories by default: edge-pair inside each journey, one story per handoff between journeys, lone scenarios alone; `edge-pair` over the whole graph and `teleport` on request) and file what they find as feedback with the backlog, on the scenario version they saw, with rehearse's own triage as the first call; its views only report (a rollup, and what each tester filed and where it stands). A sandboxed agent that depends on gherkin and backlog. `mise run calibrate:rehearse` tunes its thresholds (needs the decision model; ask first).
- Naming: `agent-*` agents, `provider-*` providers, `plugin-*` graph and service plugins. Agents run `trusted` (in the core, first-party only) or `sandboxed` (SES, any plugin).
- First-party plugins build to their `dist/` with `mise run build:plugins` (also the `build` task of `packages/plugin`, which tests and `mise run zarg` depend on); it records their hashes in `packages/plugin/src/server/first-party-hashes.ts`.
- `packages/cli` (`@zarg/cli`): the `zarg` CLI. `zarg [--thread <id>] [--focus <node>]… [--attach]` opens the TUI: one core per session, started by the TUI as its child and stopped when it quits (a core left by a session that is gone is replaced; a live session's or a headless core is refused, and `--attach` joins it instead); `zarg core start --headless`, `zarg core stop`, `zarg core status` manage a detached core; the other subcommands are graph tools. Run it with `mise run -q zarg -- <command>`. `mise run smoke:chat` runs one live driver item (needs the configured driver model; ask first).
- `packages/model` (`@zarg/model`): `Env` and `Secrets` (varlock), config loader, `Model` service, provider contract, OpenRouter-wire client. Roles fall back to `roles.default` (`config.roles` is live: `Config.reload` updates it in place); env loads the providers' schemas and `~/.config/zarg/` in any project, then the project's own `.env.schema`; `Config.setUserConfig` edits `~/.config/zarg/config.toml` (line-preserving).
- `packages/provider-zarg-router`, `packages/provider-openrouter`: provider plugins. Each ships its `.env.schema` fragment.
- `packages/decisions` (`@zarg/decisions`): `Decisions` service (JEV `/systemone`, structured fallback).
- `packages/kernel` (`@zarg/kernel`): yieldable service definitions, the manifest they generate, and the Bun Worker kernel that typechecks and runs cells.
- `packages/rlm` (`@zarg/rlm`): the RLM (unit of agency): presets and spawn graph, scoped core services (`Graph`, `Fs`, `Sh`, `Verify`, `Agenda`, `Inquire`), plugin tools as services, and the turn loop.
- `packages/core` (`@zarg/core`): `zarg-core`, one per project: hosts agents (it loads the trusted ones, like `agent-zarg`, and gives them `AgentHost`), threads and their logs (`.zarg/threads/`), the plugin host and grants, views, YOLO, and the plan and implement phases on the reconcile loop (`plan` and `implement` threads, findings on zarg's agenda); grants as the core's own prompts (`zarg.prompt` events, answered with `POST /prompts/:id`, popovers on every client); the operator's inbox (`core/src/inbox.ts`, `.zarg/inbox/`, which ignores itself): topics raised by plugins (the `Inbox` power) and the core: grants (a blocking topic; the popover is its view; no expiry unless `[plugins] grant_timeout` seconds), zarg's questions (durable: a restart keeps them open, an answer with no question waiting reaches zarg as a message; `POST /inbox/:id/reply` is chat about one), reconcile findings, and a disabled, failed or missing plugin, each change a `zarg.inbox` event on main, answered with `POST /inbox/:id/answer` (409 when not open or refused), `POST /inbox/answer` for a batch of one kind, `POST /inbox/:id/snooze|read`; blocking topics never expire and never snooze, and a restart makes open ones moot; the AG-UI API on `.zarg/run/core.sock` (token in `.zarg/run/core.json`). First-run setup (`core/src/setup.ts`): while the driver has no working model, the core opens its own Setup view (agent `core:setup`, a sheet): providers (log in: values saved with varlock to `~/.config/zarg/.env.local`, then checked), then the default model (`roles.default` in `~/.config/zarg/config.toml`) every role without its own uses; `/login` and `/models` reopen it (`POST /setup/open`).
- `packages/client` (`@zarg/client`): attach to or start a core, the AG-UI client, and `reduce` (events → thread state, including each agent's view and the inbox's topics); `priorityOf`/`sortTopics`/`openTopics` rank topics (blocking, then answers, then severity, then reports; older first; snoozed last). Never imports `@zarg/core` or a `/server` subpath.
- `packages/view` (`@zarg/view`, `@zarg/view/react`): agent views, platform-free: the section schema and `defineView`, the AG-UI view reducer, the view behaviour (focus, tabs, rows, selection) and `useView`, input layers (`dispatch`: the key goes to the top layer that takes it), surfaces (`tile`, `panel` (at the right it can be an `overlay`: a drawer over the tile area, up to 120 wide, a strip of the view left in sight), `popover`, `sheet`, `card`, and `nav`: an item above the agents that opens the plugin's view, which the plugin fills on `act` "open"; each with its own typed config, checked with `surfacesProblem`); tables can declare `search: true` (a query ranks rows by BM25 over their cells and hidden `search` text) or `toggle: true` (rows on or off, space flips them through the plugin), a row can be `busy` (the platform spins its first cell on its own clock) or `readonly` (it only reports: no mark, nothing flips), a table action can be `highlight: true` (it runs whenever the cursor lands on another row: a list whose choice fills the rest of the view) or `input: "<placeholder>"` (it asks for a line of text first, prefilled from the row's `text`; the act carries it), and a table's data can name the actions it offers now (`actions`), a `board` section is a kanban (lanes of cards; the view keeps each board's cursor and folded lanes; a click on a card opens it), a view's own actions are buttons at its top (a text section's data can name which show now, `actions`, and say it is still `loading`: the platform shows that line, with a spinner, in the middle of it), an action can drop down `choices` (the act carries the one picked), and a text can `follows` a table (it shows the text for the highlighted row) and sit `beside` it (a list and its detail side by side), and agents' key mappings per platform (`keys: { terminal, web }`, `key` for the terminal; a platform's reserved keys and a key twice where both would answer are refused). Imports no platform module (a test fails if it does).
- `packages/view-tui` (`@zarg/view-tui`): the terminal platform, drawn with the `Theme` from `@zarg/tokens` (`App` takes it; `zarg` picks the terminal palette from `ZARG_THEME_COLORS`, `COLORTERM`, `TERM`; plugins name tones, never colours) and no box in a box (sections are headed blocks): the agents rail (full height, left; glyphs only under 100 columns; an Inbox row heads its VIEWS band); home is the inbox: topics most urgent first (◆ blocking, ◇ answers, · reports), Enter opens one (its evidence, messages and numbered answers), a number answers, `t` answers with a reason, space marks topics of one kind and a number answers them all, `z` snoozes (not blocking ones), `a` shows answered ones; the status line leads with `◆ n blocking · m open`, and `g` goes to a blocking topic before agents; the grid of agent cards (`^k agents`) is paginated (zarg's sheet open over it on arrival when no plugin agent works), and shows one agent's view, zarg's conversation or the review queue (every agent's `review` tables); `^k` opens the palette, `⇥`/Esc go back; the open agent's view in the tile area, zarg's message bar under it that opens into zarg's sheet over the tile area, grant popovers over everything in the core's first-in-first-out queue, and a renderer for every section kind. Surfaces: plugin panels at the tile area's edges (shell-scope ones one per plugin and two per edge, agent-scope ones with their agent; × or Esc closes one; a drawer also closes on Esc while the view has the keys, or on a click outside it), plugin sheets and popovers, tiles a plugin opens during the operator's call; zarg's bar is agent-zarg's panel (without it: "zarg is not loaded"). Keys go through input layers: `alt+a` agents, `alt+v` the view, `alt+m` the bar (again: the sheet), `/` commands from anywhere, `g` the next agent asking for attention (◆ blinks until seen), Alt+arrows between panels; `x` archives a finished agent (with its children), `X` every finished one, and archived agents wait in a folded Archived row (`x` restores, `D` deletes for good). The core archives agents a restart stopped, and finished ones after `[agents] ttl` (default 24h; "off"). Never imports `@zarg/core` or a `/server` subpath. Web and native renderers come later as sibling packages.
- `packages/reconcile` (`@zarg/reconcile`): the reconcile loop every downstream phase runs (see intent I-0001 in the graph): affected scenarios, per-scenario git worktrees, merge, verify with fixes, one commit per pass landed on your branch, findings; each pass is a durable Effect workflow (`.zarg/run/cluster.db`).

## Secrets

- The root `.env.schema` declares every variable zarg reads (it imports the provider packages and `~/.config/zarg/`). Values live in gitignored `.env.local` files. Store secrets with varlock's device-bound encryption: `echo "$KEY" | mise x -- bunx varlock encrypt`.
- Never print, log or commit a secret value. In tests, use variable names unique to the test so a developer's real environment cannot override them or leak into output.

## Requirements

This repo's requirements live in its own zarg graph under `.zarg/graph`.

- Use the `zarg-drive` skill (`.claude/skills/zarg-drive/SKILL.md`) to refine requirements. It edits only the graph.
- Use the `zarg-implement` skill (`.claude/skills/zarg-implement/SKILL.md`) to make code match the graph when no zarg core is running (a running core plans and implements on its own). It edits only code and `.zarg/plans`.
- Never edit `.zarg/graph` files by hand. Change them through `zarg tool call`.
- Tag code that implements a scenario with a `// @scenario <id>` comment (the id as in `S-0003`), and its test. A scenario with no code yet is `planned` (`gherkin/edit-scenario {"planned": true}`). `mise run audit` (part of `verify`) fails on an untagged scenario, a planned scenario with tags, or a tag naming no scenario.

## Tasks

mise orchestrates tasks across packages:

```sh
mise tasks ls --all             # list every task in the monorepo
mise //packages/<name>:test     # one task in one package
mise //...:test                 # the same task in every package
```

A task depends on another package's task with `depends = ["//packages/<other>:build"]`.

## Setup

```sh
mise trust
mise install
mise run setup:hooks   # the fast e2e tier before every push
```

## Rules

- Run tools through mise (`mise x -- bun ...`). A globally installed bun can shadow the pinned one even inside `mise run`, so every task calls `mise x -- bun`, and tests spawn `process.execPath`, never a bare `bun`.
- Add or change a tool version only in `mise.toml`. Never document a version anywhere else.
- Use `bun`, never `npm`, `npx`, `yarn`, `pnpm`, or `node`. Use `bunx` in place of `npx`.
- Use `bun add` / `bun remove` to change dependencies. Commit `bun.lock`.
- Use `bun test` for tests and `bun run <script>` for package scripts.
- `mise run verify` typechecks and tests every package. It must pass before any commit.
- Define repeatable project commands as `[tasks]` in `mise.toml`, so humans and agents run the same thing (`mise run <task>`).
